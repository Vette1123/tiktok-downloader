# Saved 14 of 20

**Date:** 2026-09-07
**Scope:** `missedLinks.ts`, `DownloaderApp.tsx`

## What

Pasting several links at once is a free flow — the hint under the paste bar
invites it — and when some of them failed, the run said "Saved 14 of 20 links
to Recent" and stopped. That is not an answer. It is a number somebody then has
to turn back into links by comparing the summary against a Recent list they had
no reason to memorise. In practice the six are a couple of private posts and a
typo, and which is which is only knowable if the links are shown.

The failures are now collected rather than counted, listed under the summary
(five, then "and N more"), and offered back as one button. A single leftover
goes through the ordinary single-link path instead of the queue, because that
produces a result card and a real error message where the batch summary could
only manage "Saved 0 of 1".

## Mistakes

**The silent `catch` was mine, and it was labelled as a decision.** The comment
read `// skip this link — keep going through the rest of the batch`, which is
correct about control flow and quietly wrong about the visitor: continuing and
*forgetting* are different things, and the comment made the second look like
the first. It now says "keep going — but not silently".

**Declaration order, caught by the linter and not by me.** `resetResult` clears
the failure list, and it is declared above the `useState` that creates it. That
reads fine and is genuinely broken: the closure would capture a stale setter.
`react-hooks/immutability` said so in one line.

**I orphaned a doc comment two commits ago and only found it while deleting
something else.** Inserting `explain()` above `embedCaption` put three
functions between that function and its own documentation, so the comment
describing the YouTube embed caption sat above a one-line error-text helper.
Nothing failed; it was just a lie in the file for two commits. Insertions
before a documented function are worth a second look at what is now directly
under the comment.

**And a false alarm I nearly filed as a bug.** A four-link run finished with an
empty results section, which looked like the summary being cleared by something
after the batch. It was almost certainly `next dev` rewriting the AGENTS.md
block and hot-reloading the tree mid-run. A second, instrumented run polled the
DOM every three seconds and showed the whole sequence — "Resolving link 2 of
2", then the summary, then the panel — proving the flow was never broken.
**Poll the state before theorising about it.**

## What worked

- **Moving the three helpers into `lib` once they existed.** `shortLink` has
  real edge cases — an unparseable string, a trailing slash, a query string
  full of signing — and none of them were testable while it lived in a
  component file.
- **Dropping the query string.** These URLs are mostly tracking and signature;
  cutting it is what lets the identifying half survive `truncate` on a phone.
- **Singular copy.** "One link did not resolve" / "Try it again" — the plural
  branch is two lines and stops the panel reading like a form letter.

## Rules

- **Counting a failure is not reporting it.** If somebody has to reconstruct
  which items failed, the summary did not do its job.
- **A silent catch needs a comment about the *visitor*, not the loop.**
- **When inserting above a documented function, check what the comment now
  sits on.**
- **A weird one-off in the browser during `next dev` is a hot reload until
  proven otherwise.** Reproduce with instrumentation before writing it down as
  a defect.
